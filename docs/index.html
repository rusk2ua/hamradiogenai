The Grounded Builder

Amateur Radio has always been a maker's hobby. We didn't stop building when tubes gave way to transistors, or through-hole to surface mount. Software has been the wall for many of us: hardware follows physics, but software can feel like a labyrinth of syntax, toolchains and frameworks.

Generative AI is a new building material, like copper wire or silicon. It handles the syntax. You still decide what to build, and you still decide whether it works.

Ask a generic chatbot a generic question and you get AI slop: bloated, buggy, plausible-looking code. The fix isn't a better chatbot. It's three habits.

1. Curate before you code

Never let the model guess the rules or the formulas. Hand it the primary source:

  • the contest sponsor's rules (the ARRL rules PDF, not a web search for them)
  • datasheets and application notes
  • a real sample log, in the exact format you'll feed it
  • the math you trust: path loss, Maidenhead conversion, a scoring table

Left to search the web on its own, a model can land on out-of-date or non-authoritative sources. Curation is the filter.

2. Isolate the context

One project, one folder, one conversation. Give it only the sources that matter to this project. Mixing your EME siting calculator and your remote keyer in one thread blurs both.

3. Be the control operator

The AI writes syntax. Logic, error boundaries and compliance stay yours. You are the architect; the AI is the high-speed technician. In practice that means:

  • check output against the rules document and against real logs, not by reading the code
  • ask for tests that pin the important numbers (a multiplier table, a timing budget) to the source
  • write down what you haven't verified yet

Two real examples from 10ghz-log-analyzer: a blank spreadsheet row that was forward-filled into a phantom duplicate QSO (fixed in v1.5.1), and band multipliers above 122 GHz that didn't match section 5.2 of the rules (fixed in v1.6.1). Both looked fine at a glance. Both were caught by checking against the rules and real logs.

Prompting: the staircase and the anatomy

Climb the Progressive Prompting Staircase

Never ask for the whole application in one prompt. Build it in steps, each on working code from the last, so you're never debugging five new problems at once. It's the same as bringing up a microwave chain: LO, then mixer, then PA, then sequencing.

  1. Spec and architecture. Write down the requirements and the approach before any code.
  2. File in, file out. "Read this Cabrillo log and print the QSO count."
  3. Core logic and math. Parsing, distance and bearing, scoring.
  4. Visuals and interface. Maps, plots, a web page.
  5. Polish, test, document. Edge cases, tests, README, changelog.

The one rule to say first

Always ask me clarifying questions before you begin writing code.

It forces the model to work from your constraints instead of guessing. Better still, its questions surface design decisions you hadn't made yet.

Anatomy of a strong technical prompt

Part What it says Example
Role Who the AI is and what it values "You're a Python developer who values clean, single-file scripts."
Context What you're building and why "A grid-square map of a 10 GHz contest log, to share with other rovers."
Constraints The hard limits "Python only, runs on Mac and Windows, no database. Score per the attached rules."
Input The shape of your data "A Cabrillo 3.0 log. Sample attached."
Output The deliverable "One high-resolution PNG per band, darker grids for more contacts."

Not a developer? Leave the libraries out. Describe the picture you want and where it will run (your own computer, or a cloud account). The model will choose sensible libraries. If you are a developer, name them.

Prompt library

Templates modeled on how the projects in the gallery were built. Copy one, replace the bracketed parts, attach your source material, and start a fresh conversation per project. Every one assumes you've said: "Ask me clarifying questions before you write any code."

1. Score a contest from the official rules

Pattern behind 10ghz-log-analyzer.

You're a Python developer who writes clear, well-commented scripts for
non-programmers. I'm a ham radio contester, not a developer.

I've attached the official rules for [CONTEST NAME] and a sample log in
[Cabrillo 3.0 / CSV with columns ...]. Score the log exactly as the rules
say. Do not look up the rules anywhere else. If the rules are ambiguous,
stop and ask me.

Start with step 1 only: read the log and print the number of QSOs per band.
Then we'll add scoring, then reports, one step at a time.

When we get to scoring, add a test that pins every multiplier and point
value to the rules section it came from.

2. Map grids worked from a log

Pattern behind grid-mapper.

I want a map of the Maidenhead grid squares in a contest log, one image
per band, with darker squares for more contacts and labels only on grids
I worked. Input is a Cabrillo log (sample attached). It should run with one
command on Mac or Windows. I don't know which mapping libraries to use;
pick sensible ones and tell me why. Size the map automatically to the area
the log covers.

3. Revise someone else's firmware, with credit

Pattern behind ve2ug-optical-beacon-project.

Attached is [AUTHOR, CALL]'s original sketch and documentation for
[PROJECT]. Review the firmware for timing and robustness problems and
propose fixes, but don't change the core behavior without asking.

Then set it up as a GitHub repo:
- README with a version table and a test-status table (what's verified,
  what isn't)
- CHANGELOG with "Added", "Changed", "Unchanged" (what's still the original
  author's) and the reason for each change
- credit the original author everywhere the design is described
- no real credentials in the code; placeholders with a warning
Convert the original PDF docs to Markdown under docs/.

4. Turn a design decision into a calculator

Pattern behind tools/tia_calc.py in optical-receive-chain.

I'm building a photodiode transimpedance amplifier: [PHOTODIODE] at
[BIAS], [OP-AMP], target flat response [F1] to [F2]. Datasheets attached.

Don't just tell me Rf and Cf. Write a small Python script, standard library
only, that calculates stability margin, bandwidth, noise and DC headroom,
with presets for [OP-AMP LIST], and prints a table. Say in the output which
numbers are ballpark datasheet values I should measure on my own build.

Swap in your own problem: path loss and link budget between two grids, rain fade at 24 GHz, dish wind load, feed offset.

5. Specify a station system before building it

Pattern behind remkey.

I want to [GOAL, e.g. send CW with my own paddle to my shack remotely].
My station: [RIG, interfaces, what runs on the shack PC, how I reach it
remotely, what I won't change]. Constraints: [safety, latency, budget,
parts on hand].

Before any code, write docs/build-plan.md: the architecture, the failure
modes and what the system does in each (especially link loss while
transmitting), a parts list, and a phased build and test plan. Ask me
about anything you'd otherwise assume.

When we write code: tests that run without hardware, a simulation of the
firmware if possible, and CI on every push.

6. Put a web front end on a working command-line tool

Pattern behind 10ghz-web-logger-analyzer.

My command-line tools [REPO LINKS] work and are tested. Build a web front
end that runs them unmodified (vendor them in with a sync script; never
hand-edit the copies). Users upload a log and download results.

Add a test proving the web app's outputs match the CLI's for the same log.
Deploy target: [my own computer only / AWS serverless / GitHub Pages
static site]. Give me a local mode that runs without the cloud.

7. Your house rules (set once)

Put this in a project's instructions, or ask Claude to remember it.

House rules for all my GitHub projects:
- Commit as [NAME] <[ID]+[USER]@users.noreply.github.com>. Never use my
  personal email.
- Versioning: [date-based YYYY.MM.DD / semantic].
- Every change gets a CHANGELOG entry with the reason.
- README always has: what it is, how to run it, current version, and what
  has and hasn't been tested.
- No secrets in the repo. Placeholders plus .gitignore.
- Credit upstream authors. Link restricted datasheets; don't copy them.

8. Report a bug so it gets fixed properly

I ran [COMMAND] on [INPUT, attached] and got this:

[PASTE THE FULL ERROR OR WRONG OUTPUT]

Expected: [WHAT THE RULES / DATASHEET SAY IT SHOULD BE].
Find the root cause before changing anything. Fix it in place, add a test
that would have caught it, and add a CHANGELOG entry that says who is
affected.

What good looks like: the repo checklist

Every project in the gallery aims for this. None of it is hard, and the AI will do nearly all of it if you ask once and make it a house rule.

  • README that says what it is, how to run it, the current version, and what has and hasn't been tested
  • CHANGELOG with the reason for each change, and who a fix affects
  • One versioning scheme, used consistently (date-based YYYY.MM.DD or semantic 1.6.1)
  • A LICENSE, and credit for any upstream author whose work you built on
  • Sample data, so a fresh clone runs immediately
  • Tests, and CI that runs them on every push
  • Tests that pin the important numbers to their source: multipliers to the rules, timing to the spec
  • No secrets: placeholders for credentials, and a .gitignore for local files, virtual environments and .DS_Store
  • Commits use your GitHub noreply email, never your personal one
  • Link restricted datasheets; don't copy them into the repo
  • State what you haven't verified. "Not yet run on real hardware" is a feature, not an embarrassment

Protect your email before your first commit

Commits are public and permanent. Find your noreply address in GitHub Settings → Emails (it looks like 1234567+yourname@users.noreply.github.com), then:

git config --global user.email "1234567+yourname@users.noreply.github.com"

In the same Emails settings you can turn on "Block command line pushes that expose my email." Then tell your AI tool to use the noreply address for every commit.

MCP: connecting AI to your data, safely

The Model Context Protocol (MCP) is a standard plug between an AI assistant and your data or tools, much as a TNC connected a radio to a computer for packet. With an MCP server connected, you can ask things like:

  • "Graph 10 GHz QSO counts by year for the last five years from the logs in my Logs folder."
  • "Compare my QSO rates in ARRL DX and CQWW over the last three years."
  • "Using only official AWS documentation, give me a step-by-step deployment process for ..."

That last pattern is grounding again, through a different pipe: connect an authoritative documentation server, then tell the model to use only it.

My ham-mcp project is a simple example: it lets an AI query ADIF and Cabrillo logs, and PDFs, stored in Google Drive or Amazon S3.

The catch: a security minefield

As of May 2026 (figures cited in the Proceedings paper):

Figure What it means
22,775 MCP servers listed in the Glama directory. Most are weekend projects
36.7% of public MCP servers carry server-side request forgery (SSRF) vulnerabilities
41% have no authentication at all, including my own ham-mcp
8.5% use OAuth

These numbers will have moved; the lesson hasn't.

Where to start

  1. Vendor-maintained servers first: the Filesystem server, GitHub's official MCP server, and cloud providers' documentation servers.
  2. Add community servers only once you can read their code and know what they can reach.
  3. Give each server the least access it needs: one folder, not your home directory; read-only where possible.
  4. Not every AI environment allows MCP connections. Check your tool's connector settings.

Step-by-step: from idea to a shared GitHub project

This walks you through setting up Git and GitHub, building in a local folder with your AI companion, and publishing from the terminal.

Step 1: Create your online hub

  1. Create a free account at github.com.
  2. Install the official GitHub CLI: - Mac (Homebrew): brew install gh - Windows or Linux: download from cli.github.com
  3. In a terminal (Terminal, PowerShell or Command Prompt), run:

bash gh auth login

Follow the prompts to sign in through your browser. No passwords typed into the terminal.

Step 2: Protect your email address

Before your first commit, set Git to use your GitHub noreply address. Find it in GitHub Settings → Emails:

git config --global user.name "Your Name, CALL"
git config --global user.email "1234567+yourname@users.noreply.github.com"

While you're there, turn on "Block command line pushes that expose my email."

Step 3: Start a project folder

mkdir ~/my-ham-radio-project
cd ~/my-ham-radio-project
git init -b main

Add a .gitignore so Git skips local clutter:

.venv/
venv/
__pycache__/
*.pyc
.DS_Store
.env

Step 4: Build with your AI, in that folder

  1. Open the Claude desktop app and point it at ~/my-ham-radio-project.
  2. Attach your source material: the rules, a datasheet, a sample log.
  3. Start up the staircase with step 1. For example:

Ask me clarifying questions before you write any code. I want a Python script named log_parser.py in this folder that reads the Cabrillo log contest.log and prints the number of contacts per band.

  1. When something breaks, give it the evidence:

I ran the script and got this error: [paste]. Find the root cause and fix log_parser.py in place.

  1. Ask for a README and a CHANGELOG as you go, not at the end.

Step 5: Publish to GitHub

Start private; make it public when you're ready to share.

gh repo create my-ham-radio-project --private --source=. --remote=origin
git add .
git commit -m "First working log parser"
git push -u origin main

After that, each update is:

git add .
git commit -m "Describe what changed and why"
git push

To share later: repository Settings → General → Danger Zone → Change visibility. To share privately, add collaborators under Settings → Collaborators.

Step 6 (optional): Free web hosting with GitHub Pages

If you built a web page or dashboard (like nyqp-dashboard):

  1. Put the web files (index.html and friends) in a docs/ folder.
  2. Add an empty docs/.nojekyll file so GitHub serves the files as they are:

bash touch docs/.nojekyll git add docs/ git commit -m "Add web page" git push

  1. On GitHub: Settings → Pages → Build and deployment, source Deploy from a branch, branch main, folder /docs. Save.
  2. A minute or so later it's live at https://your-username.github.io/my-ham-radio-project/.

On a free GitHub account, Pages needs a public repository, and the published site is public.

Connecting Claude to GitHub

You can also connect Claude to your GitHub account so it can read and update your repositories directly. Ask Claude: "How do I connect you to my GitHub account?" and follow the current instructions for your plan. See also GitHub's getting started docs.

Common questions

"Doesn't AI just produce slop? It can't write real radio software." Ask a chatbot with no context and you'll often get exactly that. Give it the rules document, the datasheet and a sample log, build in small steps, and check the output against those sources, and you get tools you can trust on contest weekend. The difference is curation and verification.

"Isn't this cheating? Real hams write their own code." Hams didn't stop building when we moved from tubes to microchips. AI handles the syntax and typing. The system design, the testing and the judgment about whether it's right are still yours.

"Do I need to pay?" The free tiers are capable enough for a first project. Paid plans (roughly $20 a month at the entry level) make sense once you're running bigger multi-file projects or hitting usage limits. Check current pricing for your tool.

"What about my private logs?" Work in a local folder and give the AI only the files the task needs. Be aware that whatever the AI reads is sent to the model to be processed, so check your account's data and privacy settings, and keep anything sensitive out of the folder. MCP servers you run yourself let you control exactly what the AI can reach; see MCP safety.

"I'm not a programmer. Can I really do this?" Yes. I'm not one either. Describe what you want the output to look like and where it should run, and let the model choose the libraries. Your job is knowing what "right" looks like.

"Which tool should I start with?" See the workbench. I use Claude for nearly everything now.
